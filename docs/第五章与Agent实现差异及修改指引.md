# 第五章原稿与已实现 Agent 流程的差异及修改指引

## 1. 文档用途

本文档用于指导修改论文《第5章 基于演化证据约束与多智能体协同的智能建造关键技术发展研判》。对照对象包括：

- 第五章原稿：`第5章_基于演化证据约束与多智能体协同的智能建造关键技术发展研判_重构审阅稿.docx`；
- 当前项目中已经实现的证据包、命题审查、多智能体编排、路线图与方法评价流程；
- OpenSpec 变更：`align-forecast-agent-with-evolution-evidence`。

本文档不是第五章的替代稿，而是后续交给 AI 修改第五章时使用的“事实底稿＋差异清单＋改写约束”。修改时必须区分以下三种状态：

1. **已经完成软件实现并通过测试**：可以把“拟设计、拟实现”改为“构建、实现、采用”，但只能说明系统功能已经实现。
2. **已经具备运行能力，但尚未取得论文真实运行产物**：不得写成已经形成实证研判结果；需要先导入、审核和冻结真实证据包，再运行模型。
3. **尚未完成独立人工标注和对照实验**：不得声称多智能体优于单智能体，也不得报告虚构的准确率、稳定性或成本优势。

## 2. 总体判断

第五章原稿的研究逻辑与当前 Agent 的总体方向高度一致，尤其是以下内容已经正确：

- 以第四章九个主题 T01—T09 为固定研判对象；
- C01—C06 保留为候选对象，不自动提升为新主题；
- 区分主题事实、IPC 节点指标、静态语义关系和未来情景；
- 不把 IPC 节点中心度直接写成主题增长率、工程性能或成熟度；
- 将命题分为历史观察、条件外推、目标情景和证据不足；
- 设置演化分析、命题生成、反向审查、工程评审和综合裁决五类研究责任；
- 强调局部修订、支持等级、证据不足和未解决异议；
- 不以多智能体角色的一致意见代替证据强度；
- 不在缺少实证评价时声称多智能体方法更优。

原稿的主要问题不是研究方向错误，而是**仍按“拟建系统”描述，而项目已经实现了更细粒度、可运行和可追溯的流程**。尤其需要更新第5.3节和第5.7节，同时补强第5.1、5.2和5.5节的操作性描述。

还需要保留一个关键边界：当前代码实现与软件测试能够证明“流程可以按契约运行”，不能证明“面向2040年的发展判断真实”或“多智能体方法在经验上优于基线”。

## 3. 已实现 Agent 的基准流程

第五章修改时，应以下列流程作为系统事实：

```text
第四章证据整理
  → 创建证据包草稿
  → 证据包审核
  → 冻结证据包并生成 checksum
  → 人工证据审核门
  → 按 T01—T09 并行开展演化分析
  → 按对象生成原子化发展命题
  → 确定性引用、数值和推断边界校验
  → 反向审查与工程审查并行执行
  → 裁决：接受 / 修订 / 降级 / 暂缓
  → 对受影响命题进行局部修订
  → 重新校验和重新双审，直至通过或达到修订上限
  → 仅使用接受或降级接受的命题构建主题路线图
  → 开展跨主题综合
  → 最终语义与引用校验
  → 人工命题审核门
  → 发布条件检查
  → 人工发布审核门
  → 完成、导出或保留部分失败状态
```

### 3.1 三种任务模式

| 模式 | 用途 | 与第五章的关系 |
|---|---|---|
| `thesis_evolution_forecast` | 使用已审核、已冻结的第四章证据包形成命题、审查、裁决和路线图 | 第五章的正式研判模式 |
| `ipc_fusion_discovery` | 保留原项目中的IPC组合发现、确定性概率与候选概念生成 | 只作为发现工具，不直接改变T01—T09 |
| `legacy_read_only` | 读取旧版置信度和TRL结果 | 仅用于兼容，必须标记为旧语义 |

发现模式的结果只有经过人工审核、映射到既有 T/C 对象并说明模型来源与局限后，才能作为 `derived_model_evidence` 写入证据包的新版本。它不能自动创建、合并或重命名论文主题。

### 3.2 证据包生命周期

证据包采用追加式版本管理：

```text
draft → reviewed → frozen
```

冻结版本不可覆盖。补充证据、修正来源或导入经审核的发现结果时，必须创建新版本，并保存 checksum、版本历史和差异记录。

证据包包含：

- T01—T09，以及可选的 C01—C06；
- Q 类主题事实、N 类网络观察、H 类静态语义关系、M 类方法指标；
- 可选的外部工程来源和经审核的派生模型证据；
- 阶段、数值、单位、IPC、来源位置、关系依据、限制、`supports` 和 `does_not_support`；
- 可选的 IPC—专利—主题映射附件和代表专利；
- 映射材料的提供与核验状态。

映射状态应使用以下四种明确语义：

- `supplied_verified`：已提供且已核验；
- `supplied_unverified`：已提供但尚未核验；
- `reported_but_not_supplied`：论文报告已完成，但本次输入未提供逐条记录；
- `unavailable`：当前没有相关记录。

论文所述“已将筛选节点映射至阶段2、阶段3的具体专利，共926件”，在未提供逐行表时应记录为 `reported_but_not_supplied`，不能改写成“未完成映射”，也不能据此声称某个 IPC 已逐条归属于某主题。

`null` 表示未知、缺失或尚未核实，不能用 0 代替。只有来源明确记录的零值才是有效数值。

### 3.3 五类研究责任与一个执行辅助器

| 组件 | 输入 | 输出与权限边界 |
|---|---|---|
| 演化分析智能体 | 冻结证据、对象定义、缺失项 | 形成带来源的观察摘要，不补算或修改网络数值 |
| 发展命题生成智能体 | 原始证据、演化摘要、研判时域 | 形成原子命题，不新增历史事实 |
| 反向审查智能体 | 同一命题版本及原始证据 | 检查竞争解释、时间泄漏、因果越界、范围漂移和成熟度越界 |
| 工程审查智能体 | 同一命题版本及原始证据 | 检查任务、接口、环境、安全、可靠性、授权和验证条件 |
| 裁决智能体 | 命题、确定性发现、两类独立审查 | 作出接受、修订、降级或暂缓决定，不按多数表决 |
| 局部命题修订器 | 目标命题和指定问题 | 只修改受影响命题字段，不能修改对象、证据包或旧版本 |

第五章仍可称为“五类智能体职责”。局部命题修订器是受裁决驱动的执行辅助器，不宜包装成具有独立研究立场的第六类专家。

### 3.4 命题是基本审查单元

当前系统不再以整段主题预测作为最小单元，而是使用不可变、可版本化的 `DevelopmentClaim`。每条命题至少包括：

- 命题标识、版本和父版本；
- 对象编号；
- 命题类型与目标时期；
- 场景和命题陈述；
- 证据编号、推理桥梁和数值断言；
- 假设、使能条件和验证要求；
- 竞争解释、不确定来源和未解决缺口；
- 证据支持等级和命题状态；
- 修订原因。

一条文字如果同时包含“历史事实＋原因解释＋未来能力＋实现年份”，应拆分为多条可独立审查的命题。修订不会覆盖旧命题，而是形成新版本，并链接原版本、问题和修改原因。

### 3.5 确定性校验与模型语义审查分离

系统实现了三类确定性校验：

1. `ReferenceValidator`：检查对象、证据编号、证据包成员关系、阶段、IPC、日期和来源位置；
2. `NumericClaimValidator`：检查结构化数值、单位、方向、阶段和对象是否与原记录一致；
3. `InferenceBoundaryValidator`：检查以下越界转换：
   - IPC 节点 → 整体主题；
   - 网络中心度 → 工程性能；
   - 静态语义关系 → 动态加速；
   - 专利活动 → 技术成熟度；
   - 领域生命周期 → 单项主题生命周期；
   - 目标情景 → 已观察事实。

随后再由模型判断语义支持属于完整支持、部分支持、矛盾或无法判定。论文应明确：“引用编号合法”和“引用能够支持完整命题”是两个不同问题。

### 3.6 双审查、裁决与局部闭环

反向审查和工程审查针对同一命题版本并行执行，二者都能访问相关原始证据，但彼此不读取对方的草稿。裁决不是票数统计，而是根据证据与问题作出：

- `accept`：命题可进入路线图；
- `revise`：仅修订受影响命题；
- `downgrade`：降低支持强度后进入路线图；
- `defer`：证据或条件不足，暂缓进入路线图。

修订后的命题必须重新经过确定性校验、反向审查和工程审查。达到预设修订上限仍未解决时，命题进入 `revision_exhausted`，但不会阻塞其他命题。

审查发现具有稳定编号、严重程度、处理建议和打开／关闭／保留状态。关闭发现时必须指向解决该问题的新命题版本，不能仅因为文字发生变化就认定问题已解决。

### 3.7 三个人工审核门

系统包含三个可中断、可恢复的人工审核点：

1. **证据审核门**：确认第四章输入边界、映射状态和缺失说明；
2. **命题审核门**：检查命题、引用、双审查和裁决，人工修改会创建新的权威命题版本；
3. **发布审核门**：检查路线图、跨主题关系、未解决缺口和结果覆盖率。

审核可作出批准、编辑或拒绝。任务支持检查点恢复、取消和幂等重试。

### 3.8 路线图与跨主题综合

路线图只允许引用 `accepted` 或 `downgraded` 命题版本。每个里程碑包含：

- 目标时期与能力；
- 引用的命题版本；
- 前置能力与进入条件；
- 验证指标；
- 情景假设；
- 证据编号；
- 保留异议；
- 可选 TRL。

TRL 只有在提供明确量表和成熟度证据编号时才能填写。否则使用能力描述和验证条件，不生成模型自评等级。

跨主题关系必须标记其依据是网络观察、静态语义关系、经审核的模型证据，还是工程功能假设。跨主题综合读取完整命题与路线图，而不是只读取主题摘要。

## 4. 按第五章结构的差异与修改要求

### 4.1 章首导言

**原稿状态**：研究目标和证据边界基本正确，但“构建方法”和“尚未获得完整运行”同时出现，容易让读者无法判断系统是否已经实现。

**修改要求**：

- 明确本章已经实现了证据约束的多智能体工作流；
- 明确软件实现验证与预测有效性验证是两回事；
- 保留“面向2040年的是条件性路径，不是确定年份预测”的边界；
- 如果尚未用论文真实冻结证据包完成正式模型运行，不能把5.4写成系统实证输出。

**建议表述**：

> 本章在第四章演化证据包基础上，实现了以原子发展命题为核心的多智能体研判流程。该流程通过确定性证据校验、独立双审查、证据裁决、局部修订和人工审核门约束从历史观察到未来情景的推断。系统实现和流程测试证明了各环节能够按既定契约执行，但面向2040年的命题仍属于条件性研判；在完成真实证据包运行、独立标注与对照实验之前，不将其解释为已经验证的预测结果或多智能体优越性证据。

### 4.2 第5.1节：对象与演化证据输入

**保留内容**：T01—T09、C01—C06、Q/N/H/M、阶段窗口、来源独立性、未来情景与历史证据分开等内容均可保留。

**需要补充**：

- 证据包契约名称和版本；
- `draft → reviewed → frozen` 生命周期；
- checksum、diff、不可覆盖和新版本追加机制；
- 四种映射状态；
- 可选映射附件和代表专利不构成每主题强制字段；
- 发现模式证据只有经人工审核后才能导入；
- 只有冻结证据包才能启动正式论文研判任务。

**必须谨慎修改的句子**：

原稿写“当前初版包含……”。若论文真实 JSON 尚未通过系统导入、审核和冻结，应该改为：

> 当前材料已经形成证据包初稿；系统能够对其执行格式校验、人工审核、冻结和版本追踪。正式研判运行以审核后冻结版本为输入。

只有在真实证据包已经完成上述操作后，才能写明实际 `packet_id`、版本号、checksum、记录数量和映射状态。

### 4.3 第5.2节：多智能体协同机制

**原稿状态**：五类职责划分与实现基本一致。

**需要更新**：

- 在表5-1中增加“是否可修改证据”“是否可修改命题”“输出结构”三项边界；
- 补充局部命题修订器，但说明其不是第六个独立专家角色；
- 明确反向审查与工程审查独立并行，读取相同命题版本和原始证据；
- 明确裁决只有 `accept/revise/downgrade/defer` 四类动作；
- 明确审查单元是原子命题，不是完整主题叙述；
- 明确确定性校验器属于执行约束，不属于模型智能体；
- 明确工程审查模型不等于真实工程专家背书。

### 4.4 第5.3节：LangGraph编排与结果约束

这是需要修改最多的部分。

#### 4.4.1 删除或重写已经过时的现状描述

原稿第5.3.1中关于“现有技术说明仅有主链路、最多五线程、整主题重生成、只修正一次、不再次评审、无图级持久化检查点”的描述，是修改前系统的问题。当前系统已经完成相应重构，不应继续作为现状描述。

可以将该段改成“原系统与重构系统的差异”，也可以直接替换为当前流程：

- 图由 LangGraph 条件边驱动；
- 按主题并行演化分析和命题生成；
- 按命题执行确定性校验和独立双审查；
- 裁决后只修订受影响命题；
- 修订后必须重新校验和重新双审；
- 每条命题独立终止；
- 保存图检查点、节点事件和完整状态；
- 三个人工审核点支持中断与恢复；
- 跨主题综合读取完整命题、路线图、前置条件和保留异议。

#### 4.4.2 将“拟以LangGraph组织”改成“采用LangGraph组织”

可以报告已经实现的节点顺序、条件分支和状态字段，但不要把单元测试通过写成预测有效性已经得到证实。

#### 4.4.3 更新有限修订机制

原稿“本研究拟按受影响命题开展局部修正”可改为：

> 本研究按受影响命题执行局部修订。裁决为 revise 的命题由局部修订器生成新版本，随后重新接受确定性校验、反向审查和工程审查。修订次数达到运行清单预设上限后，该命题进入 revision_exhausted 状态，其他命题继续执行。

#### 4.4.4 补充命题和发现的不可变谱系

需要增加以下内容：

- 命题修订产生新版本，不覆盖旧版本；
- 人工修改也产生权威新版本；
- 审查发现通过新命题版本关闭；
- 裁决与命题版本一一对应；
- 导出结果保留命题版本、问题、裁决和关闭关系。

#### 4.4.5 更新终止状态

建议使用系统实际状态：

- `accepted`；
- `downgraded`；
- `deferred`；
- `insufficient_evidence`；
- `revision_exhausted`；
- `execution_failed`；
- `cancelled`。

正文应报告各状态覆盖率，不能只展示成功命题。

#### 4.4.6 更新图5-3

图5-3应显示：冻结证据包、三个审核门、并行主题分析、逐命题确定性校验、并行双审查、四路裁决、局部修订回路、路线图、跨主题综合、最终校验和多种终态。

### 4.5 第5.4节：关键技术发展路径研判

本节目前明确说明内容“尚非新多智能体机制的实际运行输出”。这一表述在尚未运行真实冻结证据包时必须保留。

后续有两种合法写法：

#### 方案A：尚未完成真实运行

- 保留现有九主题条件性分析；
- 将其定位为“基于第四章证据和2040材料的研究者综合分析”；
- 不称其为多智能体运行结果；
- 用作后续正式运行的任务模板、对照材料或案例说明。

#### 方案B：已经完成真实运行

- 以正式导出的命题、审查、裁决、路线图替换或重组现有叙述；
- 每项关键判断应关联命题ID、版本、证据ID和支持等级；
- 每个主题同时报告接受、降级、暂缓、证据不足或修订耗尽的命题；
- 阶段路径必须列出前置条件、进入条件、验证指标和保留异议；
- 跨主题关系必须说明关系依据；
- 不将模型输出自动升级为事实。

**建议新增表格**：

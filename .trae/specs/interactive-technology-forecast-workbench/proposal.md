# 交互式技术预测工作台 - 变更提案

## Overview
- **Change Name**: `interactive-technology-forecast-workbench`
- **Summary**: 在现有智能建造2040技术预测系统基础上，新增一个面向研究人员的交互式前端页面与后端API层，实现“研究文档输入 → 技术主题抽取 → 人工筛选/补充 → 2030/2035/2040预测 → 学术化图表与结论输出”的完整工作流。
- **Purpose**: 将当前脚本式预测系统升级为可审查、可交互、可复现的技术预测 Agent 工作台，使操作者能够基于已有研究文档和IPC分析材料动态构建技术主题集合，并调用现有多轮预测能力生成学术性质的技术路线、融合演化图表和最终结论。
- **Target Users**: 智能建造领域研究人员、技术预测论文作者、产业技术战略分析人员、政府或企业技术规划人员。

## What Will Change
- 新增轻量后端 API 层，封装现有预测能力，而不是重写预测内核。
- 新增前端工作台页面，支持研究文档输入、候选主题审查、预测任务配置、任务进度查看、结果图表展示和报告导出。
- 新增研究文档主题抽取模块，从文档中识别技术主题、IPC分类号、技术趋势、融合对、证据片段和摘要材料。
- 将人工筛选或补充后的主题转换为现有 `round1` 输入结构，复用 `run_round1`、`run_round2`、`run_round3`、`run_all_topics_roadmap`。
- 结果层聚焦 `2030`、`2035`、`2040` 三个预测节点，`2025` 作为基线阶段用于路线图和TRL演化展示。
- 新增面向学术表达的结构化输出，包括证据链、方法说明、置信度、不确定性分析、技术融合变化和结论摘要。

## Why
现有项目已经实现：
- 三轮技术预测流程。
- 多Agent辩论、自洽性验证、多模型集成、推理链条和回溯验证。
- 分主题技术路线图和Markdown/图表报告。

但当前系统仍以固定 JSON 输入和脚本运行为主，存在以下限制：
- 技术主题主要来自 `data/raw/topics.json`，不能方便地从新研究文档动态抽取和校准。
- 操作者无法在预测前筛选、合并、删除或补充技术主题。
- 缺少可视化任务进度和交互式结果浏览。
- 最终报告已有学术内容，但缺少面向 Web 的证据追溯、技术融合变化图和可导出结果包。

该变更补齐的是“产品交互层”和“输入校准层”，让现有预测 Agent 更适合真实研究工作流。

## Goals
- 支持上传或粘贴研究文档，并从中抽取技术主题、IPC依据、融合关系和证据片段。
- 支持操作者对候选技术主题进行筛选、合并、编辑和新增。
- 支持创建预测任务，围绕 `2030`、`2035`、`2040` 三个节点输出技术路线与发展趋势。
- 复用现有预测模块，保持现有CLI流程与输出目录兼容。
- 前端展示技术路线图、TRL演化、技术融合网络、不确定性分布、证据链和最终学术结论。
- 支持导出 JSON、Markdown，并为后续 PDF/Docx 导出预留接口。

## Non-Goals
- 不重写现有三轮预测算法和分主题路线图算法。
- 不接入外部专利数据库或论文数据库 API。
- 不进行大模型微调或本地模型训练。
- 不替换现有 `topics.json`、`high_potential_pairs.json` 和 `sample_abstracts/` 文件；新增流程应兼容它们。
- 不实现复杂权限、多用户协作或生产级账号体系。
- 不在首版中实现分布式任务队列；可先用本地任务状态文件或轻量SQLite。

## Scope
### In Scope
- 文档输入与解析。
- 候选主题抽取与证据绑定。
- 人工主题校准页面。
- 预测任务创建、状态查询、结果查询API。
- 现有预测流程服务化封装。
- 面向 2030/2035/2040 的前端图表展示。
- 学术化结论与导出。

### Out of Scope
- 真实专利数据库采集。
- 多租户权限系统。
- 云端部署流水线。
- 复杂协同编辑。
- 完整PDF排版引擎。

## Success Criteria
- 操作者可以从研究文档中生成候选主题列表，并完成筛选/补充。
- 筛选后的主题可以成功进入现有预测流程，生成 `round1`、`round2`、`round3` 和分主题路线图结果。
- 结果页面能围绕 `2030`、`2035`、`2040` 展示技术路线、TRL变化、融合变化和不确定性。
- 每条核心预测结论能追溯到至少一类输入依据：IPC、融合对、文档证据片段或人工补充说明。
- 默认命令行运行方式不受影响。

## Risks
- 文档中 IPC 和技术主题表述不标准，可能导致主题抽取噪声较高。
- 预测任务调用 LLM 成本和耗时较高，需要在前端明确显示配置与估计成本。
- 本地文件型任务状态在并发情况下能力有限，后续可能需要迁移到SQLite或队列。
- 前端可视化需要处理中文字体、长文本换行和大型图表可读性。

## Open Questions
- 首版是否只支持 `.txt/.md/.json`，还是需要同时支持 Word/PDF？
- 研究文档主题抽取是否必须调用 LLM，还是先用规则抽取 + LLM校正？
- 导出格式首版是否只需要 Markdown/JSON，PDF 是否放到后续迭代？
- 任务状态存储首版选择本地 JSON 还是 SQLite？
